# “同一个模型，为什么能答得更好或运行得更快？”自测参考答案

建议先独立作答，再检查自己是否区分了模型计算阶段、请求控制手段和服务性能指标。

## 1. 为什么两组概念不能互相替代？

Prefill 与 Decode 描述模型执行时的计算阶段：先处理全部已有输入，再逐个生成新 Token。输入控制与生成控制描述工程师可以干预的位置，例如组织上下文或调整采样规则。一个是实际计算流程，一个是控制视角，不能直接等同。

## 2. 不知道最新制度时应该先改什么？

应优先检索正确的最新制度并加入本次上下文。单纯改写 Prompt 不能凭空提供缺失的公司事实，量化只改变模型的数值表示与执行成本，也不会补充制度知识。加入证据后仍需用明确指令限制模型依据证据回答。

## 3. 为什么上下文不是越多越好？

无关历史和旧制度可能干扰模型选择真正相关的证据，甚至造成版本冲突；更多输入 Token 还会增加 Prefill 计算、KV Cache 占用和费用。上下文工程追求的是与当前步骤相关且可信的信息，而不是简单堆满窗口。

## 4. 固定批处理浪费在哪里？

生成 20 个 Token 的请求很早结束，若固定批次必须等待生成 300 个 Token 的请求，其位置可能在后续迭代中空闲。连续批处理允许已完成请求退出，并在后续迭代加入新请求，从而提高设备利用率；具体延迟收益仍取决于调度和负载。

## 5. KV Cache 为什么既省计算又占容量？

它保存历史 Token 在各层产生的 Key、Value，生成新 Token 时无需重新计算全部历史，因此减少重复计算。但缓存会随序列长度、层数、KV 头数量和并发请求增加，占用的显存可能成为同时服务更多请求的限制。

## 6. 4 位量化后为什么可能没有加速？

可能是硬件或推理框架缺少高效的 4 位 Kernel，也可能是反量化、格式转换等额外开销抵消了权重读取收益。还应同时检查模型质量、显存、首 Token 延迟、逐 Token 速度和吞吐，并确保使用真实目标负载比较。

## 7. 八个答案投票属于哪种扩展？

它属于多轨或并行的 Test-Time Scaling：增加候选数量，再通过投票聚合。只要不同候选有一定独立性且正确答案更常出现，投票可能提高成功率；但候选可能共同受到错误知识或错误提示影响，投票也无法判断多个一致的错误，同时还增加八次生成的成本。

## 8. 怎样选择要调整的环节？

先检查错误来源：若答案缺少任务事实或引用错误，优先检查检索和上下文；若证据正确但输出被截断、格式错误或随机性不合适，检查停止条件、结构约束和采样；若信息完整、生成设置合理而模型在多步推理中失败，再用更长推理、多候选或验证器试验 Test-Time Scaling。三种方案都应通过同一评测集比较质量、延迟和成本。
