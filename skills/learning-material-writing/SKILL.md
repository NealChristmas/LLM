# 中文技术学习资料写作

写作目标不是覆盖最多知识点，而是让特定学习者沿一条不中断的推理路径，得出本章的核心机制。先解决“为什么现在需要它”，再解释“它是什么”。

## 动笔前

先读取用户需求和目标文档的直接上下文。在项目目录中，必须查找并遵守 `AGENTS.md`、本地写作规范、学习者背景、知识地图、进度和课时模板。项目规范优先于本 Skill。

在脑中明确五个问题，不需要把答案写成正文里的模板栏目：

1. 读者已经确认掌握什么，哪些不能假定？
2. 本章只需要回答哪一个问题？
3. 上一章留下的什么困难，使本章成为必要？
4. 用哪一个具体例子贯穿主线？
5. 学完后读者能做出什么判断，下一章又会遇到什么新问题？

若上述信息无法从现有材料得到，先做保守且可逆的假设，并避免在假设上扩展整条课程。

## 边写边控制质量

完整章节或同时生成正文、卡片和题目时，读取 [写作流程](references/writing-workflow.md)；交付 Markdown 学习资料时还必须读取 [排版与信息层级](references/format-guide.md)。写作时遵循以下不变量：

- **围绕问题，不围绕术语。** 每一节都必须推动本章问题，不将大纲当作术语库依次定义。
- **概念由困难逼出来。** 按“具体现象 → 旧方法不足 → 需要的机制 → 概念名称”展开；不用“下面介绍”代替因果过渡。
- **一次只增加一个难点。** 优先沿用主例子；若必须换例子，说明原例为什么不足。
- **公式是解释工具。** 先说求解目标，再定义首次出现的变量；每次代入、展开、变形或求导都先说这一步为何有用。
- **图承担关系，文承担解释。** 对多步流程、层级、多对多映射或难以线性描述的对应关系使用图；简单事实不为配图而配图。
- **格式表达语义。** 标题用于导航，段落用于推理，列表用于并列项或步骤，表格用于精确对应，图用于关系，强调用于核心结论。格式不能只为了视觉变化。
- **术语和符号保持稳定。** 不为避免重复而替换已定义的技术名称；符号变化时明确映射。
- **取舍服务当前阶段。** 删掉不影响核心机制的旁支，但不删理解必需的因果和推导步骤。

## 建立学习闭环

先完成正文，再从正文抽取助记卡和自测，不得为了凑题引入新知识。

- 助记卡只回忆一个概念或关系，问题保留成立前提，答案短而可复述。
- 自测要求解释、辨析、判断或简单计算，不逐字复制卡片。
- 参考答案与题目同步生成，给结论和必要理由；如果答案需要正文未讲的前提，修正正文或题目。
- 只有项目规范或用户要求时，才使用固定数量和固定格式。

## 交付前的就地检查

交付前不要等待用户再发起审查：迅速反向检查每个新概念的来路、每个公式中的首次变量、每道题的正文依据，以及文档链接和目标预览器的格式。单独回看标题、图题、表头、列表引导句和链接文字：它们也是学习内容，不是可忽略的元数据。若 `$learning-material-review` 在当前环境可用，完整章节交付前使用其清单做一次独立复核；局部小改只检查受影响链路。

更新导航、进度和资料状态时，严格区分“已生成”“已阅读”和“已掌握”；不编造用户行为、运行结果或验证证据。

## 边界

- 不用外部链接代替正文解释，不编造引用、数据或事实。
- 不默认添加实验、代码、环境配置或新的学习路线。
- 不将作者规划、检查清单和模板说明遗留在学习者正文中。
- 不默认提交或推送版本库，除非用户明确要求。
