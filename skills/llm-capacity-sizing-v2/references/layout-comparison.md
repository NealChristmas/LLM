# 多布局理论比较

## 生成候选而不是缩放旧卡数

默认在用户未锁定布局时比较有依据的候选，覆盖至少一个参考布局和更少资源或不同Prefill/Decode配比（确有可支持证据时）。候选范围取决于模型分片、芯片内布局、框架支持和互联约束，不固定列出任意4/8/16卡，更不能假设每种整数卡数都可部署。

逐个记录：布局ID、工作组数、每组Prefill/Decode物理卡、推理实例数、每实例资源及共享范围、TP/EP等内部映射、复制和主机卸载、备用完整组数及依据。实例数不等于完整模型副本数。权重分片合法、整除、卡内驻留和跨机互联均应核验；未知不填true。只支持一种布局时如实交付单布局预算并说明边界，不能为了输出比较表编造其他布局支持。

## 每个候选独立重算

1. 权重：按新的TP/EP和共享范围重算专家/非专家、尺度、复制、草稿及卸载，不能将旧显存乘卡数比。
2. 缓存与运行：按新实例请求分配、跨卡复制、滑窗/索引/池分配重算；同时检查整卡和卡内分片。不得仅平均分摊总显存。
3. 时延：按新实例数、资源和调度重算平均TTFT与TPOT近似。不能把并行卡数增加认定为有效能力线性增长；效率、通信改变需要依据或用户认可的假设。
4. 资源条件：重算KV传输、专家通信及主机卸载资源。无法定量建模时保留未知，作为条件候选，不能写成全面可行。
5. 备用：按每个布局自己的完整组加入备用，分别比较工作卡和含备用总卡。共同需求、长度/时延口径和敏感性场景保持一致；不将一个布局乐观场景与另一个中心场景直接排名。

模型适配器输出每个候选的检查项：`memory`、`card_local`、`ttft`、`tpot`、`transfer`、`host`、`layout_support`。每项包含`ok`（true/false/null）、理由和来源或明确假设；不适用时用true并写明为何不适用。`memory/card_local/ttft/tpot`任一缺失不能进入候选；通信、主机和支持未知时可在授权粗估范围内形成条件候选。

## 比较工具契约

`scripts/compare_layouts.py`只对适配器的逐布局结果进行比较，不识别模型、不生成底层公式、不假装已计算缓存。Python接口`compare_layouts(layouts, evaluator)`逐个调用已验证的本地模型适配函数，evaluator返回checks和可选metrics。不能执行输入JSON中的代码或公式。

离线CLI接受JSON数组，每项含`layout`及该布局已计算的`evaluation`：

```json
[
  {
    "layout": {
      "id": "candidate-name",
      "workGroups": 1,
      "prefillCardsPerGroup": 8,
      "decodeCardsPerGroup": 8,
      "spareGroups": 0
    },
    "evaluation": {
      "checks": {},
      "metrics": {}
    }
  }
]
```

以上只演示输入形状，空checks会得到“计算缺项”，示例卡数不代表默认或有效配置。模型特定参数、数据来源和算法摘要由适配器另行留存。CLI为`python scripts/compare_layouts.py --input <已计算的布局结果.json> --out <比较结果.json>`，由智能体生成输入，不要求用户填理论JSON。

## 结果等级与选择

- rejected：任一声明约束不满足，保留失败理由。
- incomplete：必要容量/时延计算缺失，不参加可行候选排名。
- conditional：已完成容量/时延检查，但通信、主机或布局支持仍未知。仅用户已授权粗估时可向客户展示，始终单独列出。
- budget_candidate：所有列明检查均在有来源或明确假设的模型内满足。它也不是实测认证。

工具分别返回两类候选内的最低总卡数及所有同卡数ID，不将条件候选混成预算候选，也不自动决定采购推荐。选择建议同时考虑敏感性、时延余量、显存余量和未验证条件；没有成本/BOM时不等同于成本最优。没有候选时不机械加卡修复任意约束；先解释失败原因，决定调整布局或补依据。

报告标题使用“候选集合内最少资源方案”“参考余量方案”等，声明已评估和未评估范围。不同方案优势交叉时并列呈现，不强行选唯一方案。V2仍只做理论，不引入实测性能基线。
