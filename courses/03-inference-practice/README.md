# 推理工程实战规划：D33～D47

D01～D32 已经回答了大模型怎样工作、推理为何消耗显存，以及引擎如何优化和调度。下一阶段不再继续堆叠概念，而是固定一个模型和一套工作负载，把“部署—测量—定位—优化—复测”完整做一遍。**每次优化都必须和基线对比；能启动服务不等于完成实验。**

具体模型、引擎版本和硬件不会在规划阶段写死。D33 先盘点本机或云端资源，再选择能稳定完成全部实验的主环境；默认优先使用 NVIDIA GPU 与 vLLM 建立主线，若硬件不满足，再选择云端 GPU 或缩小模型，而不是跳过测量环节。

```mermaid
flowchart LR
    A["D33～D35<br/>环境与基线"] --> B["D36～D39<br/>服务、压测与诊断"]
    B --> C["D40～D44<br/>单项优化与公平对比"]
    C --> D["D45～D47<br/>多卡、可靠性与综合项目"]
```

## 第一阶段：建立可复现基线

这一阶段只解决“同一结果能否再次得到”。若环境、模型和输入不断变化，后面的优化数字就没有比较意义。

| 章节 | 要解决的问题 | 实践内容 | 保留的证据 |
| --- | --- | --- | --- |
| [**D33：实验环境是否满足推理要求？**](d33-environment/README.md) | 当前机器能运行多大的模型，缺少什么条件？ | 盘点 GPU 型号、显存、驱动、CUDA、操作系统和磁盘；按显存公式选择本地或云端路线 | 环境清单、版本快照、资源选择说明 |
| **D34：一个模型目录里究竟有什么？** | 下载的文件怎样共同组成可加载模型？ | 检查配置、Tokenizer、权重分片、精度与生成配置；核对模型许可证和校验信息 | 模型清单、参数与显存估算 |
| **D35：怎样建立最小推理基线？** | 后续优化要与什么结果比较？ | 用最简单的推理路径运行固定提示集，记录输出、首轮显存和端到端时间 | 固定提示集、原始输出、基线记录 |

## 第二阶段：从模型运行到可测量服务

单次脚本能生成文字，还不能说明它能服务并发请求。这一阶段把模型放进推理引擎，用稳定负载测量，并把慢拆成可定位的阶段。

| 章节 | 要解决的问题 | 实践内容 | 保留的证据 |
| --- | --- | --- | --- |
| **D36：怎样把模型变成可调用的推理服务？** | 请求怎样经过 API、队列、引擎再返回结果？ | 用 vLLM 启动服务，验证流式与非流式请求、并发请求和错误输入 | 启动配置、请求样例、服务日志 |
| **D37：怎样构造公平的推理压测？** | 不同测试结果为什么经常不可比较？ | 固定输入/输出长度分布、并发或到达率、预热和采样参数；记录 TTFT、TPOT、吞吐与完成率 | 负载说明、原始结果、汇总表 |
| **D38：怎样同时观察请求和 GPU？** | 指标变差时，怎样知道时间花在哪里？ | 对齐请求时间线、引擎日志、GPU 利用率、显存和功耗等观测数据 | 时间线、监控快照、指标解释 |
| **D39：怎样用证据定位一次性能问题？** | 该改计算、显存、调度还是负载？ | 选择一个慢场景，提出可证伪假设，做最小对照实验并形成诊断结论 | 假设表、对照结果、诊断报告 |

## 第三阶段：一次只验证一种优化

这一阶段不追求把所有开关同时打开。每章只改变一个主要变量，先检查输出质量与稳定性，再比较性能变化，否则无法知道收益来自哪里。

| 章节 | 要解决的问题 | 实践内容 | 保留的证据 |
| --- | --- | --- | --- |
| **D40：批处理与调度参数怎样影响延迟和吞吐？** | 为什么吞吐提高时单请求可能更慢？ | 改变并发、批次 Token 预算等参数，画出延迟—吞吐关系 | 配置矩阵、曲线、推荐区间 |
| **D41：上下文与 KV Cache 怎样限制容量？** | 长 Prompt 和高并发何时导致显存不足？ | 改变上下文长度与活动请求数，对照理论估算和峰值显存 | 估算表、实测表、偏差解释 |
| **D42：量化是否真的带来可接受收益？** | 少占显存是否同时更快且质量不变？ | 比较基准精度与一种低比特方案的显存、延迟、吞吐及固定样例输出 | 质量抽查、性能对比、取舍结论 |
| **D43：前缀缓存和 Chunked Prefill 何时有效？** | 哪类负载能从复用与切块中获益？ | 构造共享前缀和长 Prompt 负载，分别开关优化并复测 | 命中条件、分阶段指标、收益边界 |
| **D44：怎样公平比较两个推理引擎？** | 引擎差异与配置差异怎样分开？ | 在硬件支持时以 SGLang 作为第二候选；保持模型、精度、负载和质量条件一致 | 支持矩阵、等价配置、选型记录 |

## 第四阶段：从单卡实验走向可交付系统

单卡调优完成后，剩下的问题不只是“更快”，还包括如何扩容、发现故障和恢复服务。没有多卡资源时，D45 先完成配置设计与通信数据解读，实际多卡验证延后，不伪造结果。

| 章节 | 要解决的问题 | 实践内容 | 保留的证据 |
| --- | --- | --- | --- |
| **D45：模型放不进单卡时怎样扩展？** | 张量并行或流水线并行解决什么限制，又增加什么通信？ | 设计并在资源允许时运行双卡配置，对比单卡/多卡显存、延迟和吞吐 | 拓扑图、通信观察、扩展效率 |
| **D46：服务怎样应对过载和故障？** | 压测通过为什么仍可能无法上线？ | 验证健康检查、超时、限流、排队、优雅停止、重启与日志追踪 | 故障注入记录、恢复时间、运行手册 |
| **D47：怎样完成一次可复现的部署选型？** | 如何把零散实验变成工程结论？ | 综合部署目标模型，复跑基线与候选配置，给出容量、性能、质量、成本和风险结论 | 可复现配置、最终报告、改进清单 |

## 每章怎样学习

每章按一个 4 小时学习单元设计，但以验收结果而不是计时结束：约 30～45 分钟阅读必要机制，约 2 小时完成实验，约 45 分钟整理原始结果和对照表，剩余时间用于排错与复盘。遇到下载、编译或云资源等待时，不把等待时间算作有效学习时间。

每章资料将包含四部分：**原理简述、可复现实验、结果记录模板、验收问题**。命令和配置会在生成该章时根据 D33 确认的操作系统、GPU 与软件版本编写，不提前假设；所有实际输出由实验产生，资料不会预填“成功结果”。

## 阶段完成标准

D47 完成时，应能交付一份别人可以复现的推理服务报告，并回答四个问题：模型与负载是什么、当前瓶颈在哪里、优化为何有效或无效、现有资源能承载多少请求。**课程完成的核心证据不是运行截图，而是固定条件下可复现的对照数据和有边界的结论。**

容器编排、Kubernetes GPU 调度、多租户平台和 CUDA/Triton 算子开发不塞进 D33～D47；它们分别属于后续 AI 平台与底层性能专项。先把单个推理服务测明白，再扩展到集群或自定义 Kernel，学习链不会断裂。
