# D22：怎样判断一次推理到底慢在哪里？

D15 已学会把请求拆成上游、排队、Prefill 和 Decode；D18～D21又解释了 GPU 执行、存储、算力与容量。本章不重复定义指标，而是把这些层次组成一条可执行的诊断顺序。

## 1. “GPU 利用率高”还不能得出结论

假设服务 TPOT 很高，同时监控显示 GPU 利用率 95%。这只能说明采样期间 GPU 经常有工作，不能说明是哪类 Kernel、计算单元是否饱和、显存带宽是否饱和，也不能说明每个请求是否公平。若立即更换 GPU 或开启量化，很可能没有针对真正瓶颈。

诊断需要从用户症状逐层收缩：先确认慢在哪个请求阶段，再确认该阶段主要执行哪些工作，最后确认工作受哪种资源限制。

```mermaid
flowchart LR
    A["用户症状"] --> B["阶段：排队 / Prefill / Decode"]
    B --> C["负载：输入、输出、并发、批次"]
    C --> D["资源：计算 / 带宽 / 容量 / 调度"]
    D --> E["提出单一优化假设"]
    E --> F["同条件重新测量"]
```

## 2. 第一步：固定请求形状和到达方式

性能数据只有在条件可比时才有意义。输入长度影响 Prefill，输出长度影响 Decode 次数，上下文长度影响 KV Cache，到达速率和并发影响排队与批处理。若优化前使用短 Prompt、优化后使用长 Prompt，即使两次平均延迟不同，也无法归因于优化。

因此至少记录输入 Token 数、输出 Token 数、请求到达方式、并发上限、模型与精度、硬件和引擎配置。D16 已讲过公平对照，本章把它作为定位前提，不再展开评测设计。

## 3. 第二步：先找阶段，再看资源

| 主要症状 | 首先查看 | 可能继续下钻的方向 |
| --- | --- | --- |
| TTFT 高且排队长 | 到达速率、活动请求、调度 | 容量不足、批策略、长请求阻塞 |
| 排队短但 Prefill 长 | 输入长度、Prefill 批次 | 大矩阵计算、长上下文注意力、Chunked Prefill |
| TPOT 高 | Decode 批次、上下文、KV 访问 | 带宽、小批次、低效 Kernel、调度间隙 |
| 并发升高后 OOM | 权重、KV 预算、活动 Token | 缓存精度、块管理、长度与准入策略 |
| GPU 经常空闲 | 请求供给、CPU、同步、Kernel 间隙 | 批次太小、预处理慢、调度或通信等待 |

表中的方向不是结论。比如 TPOT 高可能来自长上下文引起的 KV 访问，也可能来自跨卡通信；需要下一层证据继续区分。

## 4. 第三步：建立可证伪的假设

“系统太慢”无法验证；“Decode 小批次导致并行度不足”可以验证。若假设成立，提高稳定并发或合并更多 Decode 请求后，计算规模应增大，TPOT 或每卡吞吐应出现可解释变化。若完全没有变化，就要回到带宽、Kernel 或其他等待原因。

一个优化实验最好只改变一个主要因素。例如先保持模型、精度和请求集不变，只调整批次上限；再保持其他条件不变测试量化。否则即使结果变好，也不知道收益来自哪里。

## 5. 平均值为什么会掩盖问题？

若九个请求很快、一个请求极慢，平均值可能仍显得尚可。线上体验还要观察 P50、P95、P99 等分位数：P95 表示约 95% 的样本不超过该值，剩余约 5% 更慢。尾部变慢常与排队、长请求竞争、抢占、缓存未命中或周期性资源争用有关。

吞吐也必须与延迟一起看。等待更大的批次可能提高总 Token/s，却增加 TTFT；严格限制批次可能改善少数请求的延迟，却降低总体容量。**优化目标应是满足延迟约束下的最大可持续吞吐，而不是孤立追求某个峰值。**

## 6. 形成诊断记录

一次完整结论应包含：症状、测试条件、阶段拆分、资源证据、假设、改动和结果。例如：“在固定输入 2K、输出 256、到达率 20 req/s 下，P95 TTFT 主要由排队构成；提高批次上限后吞吐提高但 P95 TTFT 更差，因此瓶颈不是单纯 Kernel 速度，而是负载超过当前延迟目标下的服务容量。”

D22 到这里建立的是定位方法。D23 开始进入具体优化机制，首先回答量化怎样影响权重读取、计算 Kernel 与输出误差。

## 助记卡片

**卡片 1：性能诊断为什么从用户阶段开始？**

> **答案：** 同样的总延迟可能来自排队、Prefill 或 Decode，不同阶段需要不同证据和优化。

**卡片 2：比较优化前后至少要固定哪些负载条件？**

> **答案：** 输入与输出长度分布、请求到达方式、并发、模型精度、硬件及主要引擎配置。

**卡片 3：GPU 利用率高为什么不是完整结论？**

> **答案：** 它不能单独说明具体 Kernel、计算与带宽饱和度、有效工作比例或请求延迟分布。

**卡片 4：什么是可证伪的性能假设？**

> **答案：** 它明确指出原因，并预言改变某个条件后应观察到什么结果；不符合预言时可以被否定。

**卡片 5：为什么一次实验尽量只改一个主要因素？**

> **答案：** 否则结果变化无法可靠归因到某项优化。

**卡片 6：为什么要看高分位延迟？**

> **答案：** 平均值会掩盖少量极慢请求，高分位能显示尾部体验和资源竞争。

**卡片 7：吞吐优化的合理目标是什么？**

> **答案：** 在规定延迟和质量约束下获得可持续吞吐，而不是只追求瞬时峰值。

## 自测题

3. TPOT 高且 GPU 计算、带宽利用都低，下一步应检查哪些类型的空隙？
4. 把“GPU 太慢”改写成一个可以验证的假设。
