# 机制讲解与复核

在数学、模型结构和算法类教程中使用；不要把 FFN 这一试写案例的维度、章节或配图复制为通用模板。

## 选择能解释问题的例子

最小例子必须仍保留要解释的机制。如果要解释非线性，选一个让激活实际改变中间值的输入；如果要解释注意力如何结合信息，要显示多个位置之间的关系，不能只画一个盒子再称它为上下文。一次增加一个主要条件，复用同一例子，避免频繁更换场景增加理解负担。

“具体输入 → 关键中间状态 → 输出 → 对照 → 一般表达”是可选的展开方式，不是固定章节模板。例子过长时保留关键一步，其余用表或图合并。不要解释通用编程基础，除非当前读者确实需要。

## 把结论写到计算里

不要只给输入和输出，至少展开支撑核心结论的中间计算。矩阵例子明确采用行向量还是列向量，保持公式、图和算例一致。形状是接口，数值变化是计算；不能把向量变长等同于信息变多，也不能把同宽误写为数值不变。

反事实对照保持其他条件不变。例如去掉激活后，两个线性变换可以合并；因此它能说明非线性的作用，却不能证明某模型训练效果更好。任意权重、玩具词表、教学简化就近标记。例子用 ReLU、视频用 GELU 时，解释简化的目的与不可照搬之处；没有核验时不补写真实模型参数、代码输出或实验结果。

关键数字可手算或通过短脚本核验。脚本不是学习任务，计算记录不必放在正文。真实代码教程则保留可复现的输入、依赖和执行结果，无法执行时明确说明验证范围。

## 让图承担解释

先说清图要回答什么问题，再选表现方式。流程图展示处理顺序；状态图展示数值变化；对应图展示输入坐标、输出坐标或位置关系；对比图隔离一个变化条件。清晰的表能说明的问题无需强行配图。

图中文字应能读清，箭头方向与正文相符。标出省略的关键结构，尤其避免把简化模块画成完整模型。关键结论在正文也能读到，图片不能成为理解所需信息的唯一载体。Markdown 引用本地图片用稳定的相对路径，交付时核对文件存在；需要在聊天直接展示时用绝对路径。

## 交付前自查

| 检查问题 | 不通过时怎样修改 |
| --- | --- |
| 没看原视频，能否理解输入、过程、输出与结论？ | 补足必要前提和中间步骤，不靠外链替代解释 |
| 例子是否展示了声称的机制？ | 改输入或缩小结论，不只增加一句抽象评价 |
| 反事实是否只改变了要比较的条件？ | 保持权重、输入等其他条件一致 |
| 同一句话是否混入视频事实、推断和补充？ | 分开表述，给补充依据，删去无法支撑的归因 |
| 图、公式、数字、维度是否一致？ | 核算并查看图；不把语法检查当作事实验证 |
| 易混关系是否讲清？ | 如分数与概率、层运算与模块用途、位置共享与位置交互 |
| 正文是否退化成术语列表或截图解说？ | 用具体变化接起因果，合并重复短节 |
| 是否添加了用户没有要求的学习模块？ | 删除卡片、测验或计划等附加内容 |

这一自查评估成稿，不评估读者是否已经掌握。一次试写只能证明当前案例可用，不能声称 skill 在所有课程上最优。
